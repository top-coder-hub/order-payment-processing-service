# Module 12 — Observability (Logging, Trace IDs & Audit)

## Overview

This module implements the observability foundation for the Order & Payment
Processing Service. It enables traceability, structured logging, and
auditability of critical operations without requiring external observability
infrastructure.

The goal is to make production debugging possible using only application logs
and audit records.

---
# 1. Trace ID Lifecycle

Every request processed by the service is associated with a **traceId**.

The traceId allows engineers to correlate:

- API requests
- application logs
- audit records
- service operations

## Trace ID Flow

```
Incoming HTTP Request 
↓
Micrometer/Brave tracing bridge extracts or generates trace context
↓
Automatically injected into SLF4J MDC (Mapped Diagnostic Context)
↓
Every Logback entry is stamped with [traceId, spanId]
↓
Extracted from current context and persisted in audit records
↓
Returned in API Error Responses for client-side correlation
```

TraceId is automatically generated by Micrometer Tracing and
propagated through the logging context via the Brave tracing bridge.

### TraceId resolution order:

1. MDC traceId injected by the tracing system
2. Current active Micrometer span
3. RequestId fallback


### Implementation location:

* PaymentService.resolveTraceId()
* OrderService.resolveTraceId()

# 2. Structured Logging

The application uses **JSON structured logging** via Logback.

Structured logs make it easier to:

- filter logs
- correlate requests
- analyze failures

## Logging Fields

Each log entry contains:

```
timestamp
level
service
traceId
spanId
requestId
userId
logger
thread
message
exception
```

### Example log entry:

```
{
"timestamp":"2026-01-12T04:13:10Z",
"level":"INFO",
"service":"order-payment-processing-service",
"traceId":"7c9f4a2a9d...",
"spanId":"9f2d1a",
"userId":"42",
"logger":"PaymentService",
"message":"Payment transition completed"
}
```

# 3. Key Logged Events

The service logs important domain events for operational visibility.

## Payment Events

* payment initiation
* payment success
* payment failure
* idempotency replay


## Order Events

* order creation
* order cancellation
* order state transition


## Security / Access Events

* ownership violations
* unauthorized access
* invalid request parameters


## System Errors

All unhandled exceptions are logged with:

* traceId
* error message
* stack trace


Stack traces are **never exposed to API responses**.

# 4. Audit Trail

The system maintains **append-only audit tables** to track domain state
changes.

## Audit Tables

* order_audit
* payment_audit


### Audit records allow the system to answer:

* Who performed the action?
* What action occurred?
* When did it happen?
* What was the outcome?


## Order Audit Fields

```
order_id
from_state
to_state
order_action
changed_by
trace_id
error_message
created_at
```

## Payment Audit Fields

```
payment_id
from_state
to_state
payment_action
changed_by
trace_id
error_message
created_at
```

### Audit records are written using a separate transaction:

@Transactional(propagation = REQUIRES_NEW)


### Persistence of Evidence:

By utilizing REQUIRES_NEW, we ensure that even if the business transaction rolls back, the audit record persists. This allows for the analysis of "Negative Flows" (failures) which are often more critical than successful ones.

---
# 5. Observability with Micrometer

The service uses **Micrometer Observations** to create spans for critical
operations.

These spans allow engineers to visualize execution flow and identify slow
operations.

## Span Hierarchy

```
payment.process (root span created via @Observed)

├── payment.state.transition 

└── order.update.state 
```

## Span Metadata

The root span is enriched with:

```
order.id
payment.id
status.target
```


This provides trace-level context during debugging.

### Low Cardinality (Metrics-friendly): 

status.target (Used for aggregate dashboards).

### High Cardinality (Trace-only): 

order.id, payment.id (Used for granular lookups).

This design enables correlation across logs, traces, and audit records
using a single traceId, forming a unified observability model.

---
# 6. Security Logging Rules

Sensitive information must never appear in logs.

The system explicitly avoids logging:

* authorization tokens
* passwords
* payment credentials
* secret keys
* sensitive headers


Only non-sensitive identifiers such as:

```
traceId
userId
orderId
paymentId
```

are logged.

---
# 7. Error Handling and Traceability

All API errors include a traceId so that client-reported failures can be traced
in server logs.

Example API response:

```
{
"errorCode": "INVALID_ORDER_STATE",
"message": "Cannot process payment for order",
"traceId": "7c9f4a2a9d..."
}
```

Engineers can search the traceId in logs to reconstruct the full request flow.

---
# 8. Production Debugging Workflow

Typical debugging workflow:

```
Client reports error with traceId
↓
Search logs using traceId
↓
Identify failing span
↓
Inspect audit records
↓
Determine state transition failure
```


This workflow allows root cause analysis without additional tooling.

---
# 9. Future Enhancements

Future improvements may include:

* OpenTelemetry integration
* distributed tracing backend (Zipkin/Tempo)
* centralized logging (ELK / Loki)
* metrics dashboards (Prometheus + Grafana)


These are intentionally deferred to later versions to keep the V1 system
lightweight.

This approach ensures full request traceability without requiring
external observability systems, making it suitable for lightweight
production deployments.

# Summary

Module 12 establishes the core observability capabilities required for a
production-ready backend:

- Request traceability via traceId
- Structured JSON logging
- Append-only audit trails
- Micrometer span tracing
- Secure logging practices

These mechanisms enable reliable debugging and operational monitoring without
external observability infrastructure.
